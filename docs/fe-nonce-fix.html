1. 증상

사용자가 다음 흐름 중 두 번째 step 이후에 다음 에러로 막힘:

  • Launch agent — Step 2 (registerAgent)
  • Mint shares — Step 1 (approve) / Step 2 (Pyth update) / Step 3 (deposit)
  • Redeem 흐름의 두 번째 step 이후
The contract function "approve" reverted with the following reason:
RPC submit: failed to forward tx to sequencer, err: 'nonce too low: next nonce 3115, tx nonce 3114'
The contract function "registerAgent" reverted with the following reason:
RPC submit: failed to forward tx to sequencer, err: 'replacement transaction underpriced'

두 에러는 같은 뿌리. 현재는 사용자가 매 발생 시 Metamask 활동 데이터 삭제 + self-transfer 같은 워밍업 tx로 회피 중. 데모 본방 안정성을 위해 영구 해결 필요.

이 세션의 실제 데이터:

3. 원인 분석

BE 또는 컨트랙 문제가 아님

  • BE는 user wallet으로 tx를 발사하지 않음 (admin 흐름은 BE executor wallet 별도 사용). 따라서 user wallet의 nonce에 영향을 못 줌.
  • 스마트 컨트랙은 caller의 nonce만 +1 시킴. 다른 EOA의 nonce 못 만짐.
  • FE 코드 자체도 동시 tx 안 보냄. waitForTransactionReceipt 로 receipt까지 await 후 다음 step 진행.

진짜 원인 — Metamask의 nonce 캐시 정책 + L2 testnet RPC 동기화 lag

Metamask는 매 tx마다 chain RPC에서 nonce를 조회하지 않고 내부 캐시에 의존:

  1. tx 발사 시 → 캐시된 nonce 사용
  2. 발사 직후 캐시 +1 (낙관적 업데이트)
  3. RPC에서 확인된 결과로 보정 (이상적으로는)

이 보정 단계가 Mantle Sepolia 같은 신생 L2 환경에서 자주 실패:

  • tx 가 sequencer에 도달했지만 confirm 까지 RPC 응답 lag 있음 → Metamask는 미확정 상태로 캐시 유지
  • 이전 흐름에서 실패한 tx (PriceStale, 사용자 reject 등) 의 결과가 RPC에 늦게 반영 → 캐시가 chain 실상태보다 앞서거나 뒤처짐
  • 여러 wallet을 한 세션에서 빠르게 전환 → 각 wallet의 캐시 동기화 누락

결과:

  • "nonce too low": wallet 캐시가 chain보다 작음 (실제 처리된 tx 인지 못 함)
  • "replacement underpriced": wallet이 이미 mempool에 있는 tx 와 같은 nonce + 동일/낮은 gas로 재발사 시도
이 캐시 정책은 Metamask 내부 closed-source 코드라 외부에서 수정 불가. 우리가 컨트롤할 수 있는 유일한 레이어는 FE 코드 — 거기서 Metamask 캐시를 무시하고 chain RPC에 직접 nonce를 묻는 방식으로 우회.

왜 self-transfer 가 해결책처럼 보였나

self-transfer (단순 EOA → EOA 송금)는 Metamask가 가장 안정적으로 추적하는 tx 형태. confirm 즉시 wallet이 "내 nonce는 이제 X+1" 로 강제 재인지. 이후 흐름이 정상화. 하지만 사용자가 매 nonce 에러마다 이걸 수동으로 해야 하는 건 데모 시연에 부적합.

4. 해결 방법 — 명시적 nonce + 자동 retry

두 단계를 묶어서 사실상 100% 통과:

  1. 매 writeContractAsync 직전에 publicClient.getTransactionCount({blockTag: "pending"}) 로 chain RPC에서 직접 nonce fetch → Metamask 캐시 우회
  2. nonce 관련 에러 발생 시 (race 등 드문 케이스) fresh nonce 재조회 후 1회 자동 retry

4-1. 헬퍼 함수 추가

두 패턴을 묶어주는 헬퍼를 src/lib/tx.ts 같은 새 파일에 한 번만 정의:

// src/lib/tx.ts
import type { PublicClient } from "viem";

const isNonceError = (e: unknown): boolean => {
  const msg = (e instanceof Error ? e.message : String(e)).toLowerCase();
  return (
    msg.includes("nonce too low") ||
    msg.includes("replacement transaction underpriced") ||
    msg.includes("already known")
  );
};

/**
 * writeContract wrapper that bypasses Metamask's stale nonce cache and
 * auto-retries once on nonce-class errors. See docs/fe-nonce-fix.html for
 * background.
 */
export async function writeWithNonce(
  publicClient: PublicClient,
  writeContractAsync: any, // wagmi's WriteContractMutateAsync
  userAddress: `0x${string}`,
  args: any,
): Promise<`0x${string}`> {
  const submit = async () => {
    const nonce = await publicClient.getTransactionCount({
      address: userAddress,
      blockTag: "pending",
    });
    return writeContractAsync({ ...args, nonce });
  };

  try {
    return await submit();
  } catch (e) {
    if (!isNonceError(e)) throw e;
    // small backoff so sequencer/RPC views can reconcile
    await new Promise((r) => setTimeout(r, 800));
    return await submit();
  }
}
실제 반영본 (src/lib/tx.ts) — wagmi의 제네릭 writeContractAsync 타입과 충돌을 피하려고 any 대신 submit(nonce) 콜백(thunk)을 받는 형태로 구현. 동작은 위 가이드와 동일(pending nonce 명시 + nonce류 에러 1회 재시도). 에러 판정은 viem의 cause 체인까지 훑음. 
// src/lib/tx.ts  (실제 반영본)
import type { PublicClient } from "viem";

function errorText(err: unknown): string {
  let text = "";
  let cur: unknown = err;
  for (let depth = 0; cur instanceof Error && depth < 6; depth++) {
    text += ` ${cur.message}`;
    const v = cur as { details?: unknown; shortMessage?: unknown; cause?: unknown };
    if (typeof v.details === "string") text += ` ${v.details}`;
    if (typeof v.shortMessage === "string") text += ` ${v.shortMessage}`;
    cur = v.cause;
  }
  if (!(err instanceof Error)) text += ` ${String(err)}`;
  return text.toLowerCase();
}

export function isNonceError(err: unknown): boolean {
  const msg = errorText(err);
  return (
    msg.includes("nonce too low") ||
    msg.includes("nonce has already been used") ||
    msg.includes("replacement transaction underpriced") ||
    msg.includes("already known")
  );
}

export async function writeWithNonce(
  publicClient: PublicClient,
  userAddress: `0x${string}`,
  submit: (nonce: number) => Promise<`0x${string}`>,
): Promise<`0x${string}`> {
  const run = async () => {
    const nonce = await publicClient.getTransactionCount({
      address: userAddress,
      blockTag: "pending",
    });
    return submit(nonce);
  };
  try {
    return await run();
  } catch (err) {
    if (!isNonceError(err)) throw err;
    // 시퀀서/RPC 뷰가 정합될 시간을 준 뒤 fresh nonce로 1회 재시도
    await new Promise((resolve) => setTimeout(resolve, 800));
    return run();
  }
}

8. 참고 / 보너스

  • 같은 패턴은 Mantle Sepolia 외 다른 신생 L2 testnet (Base Sepolia, Optimism Sepolia 등) 에서도 wagmi + Metamask 조합에서 자주 보고됨.
  • blockTag: "pending" + retry 는 wagmi 공식 문서 및 viem 가이드의 권장 패턴.
  • Rabby wallet은 매 tx마다 chain RPC 직접 조회하는 정책이라 이 이슈가 거의 없음. 하지만 사용자에게 특정 wallet 강제는 어렵기에 FE 코드 변경이 본질 해결.
  • 운영(mainnet) 환경에선 RPC 안정성이 더 좋아 발생 빈도는 낮지만, 이 패치는 안전망으로 유지 권장.
