1. GET /agents/{id}/decisions 응답이 501 — schema-only stub 상태

에이전트 상세 페이지의 "Decision log" 영역은 그 에이전트가 그동안 한 행동들(자산 리밸런싱, 수익 회수, 배당 분배 등)을 시간순으로 보여줘야 하는 자리인데, 전체 이력을 페이지 단위로 끊어서 가져오는 API 가 아직 비어 있어서 호출하면 매번 실패합니다. 그래서 화면에는 가장 최근 1~2건만 나오고 그 이전 기록은 사용자가 아예 볼 수 없습니다.

재현

curl -i https://web-production-acacf1.up.railway.app/agents/3/decisions?limit=10
HTTP/2 501
{"detail":{"error":"InternalError","message":"Not implemented yet — schema-only stub."}}

기대 동작

Page[Decision] 형태로 decisions 테이블에서 페이지네이션된 row 를 반환해주는 것. OpenAPI 스키마에는 이미 정의되어 있어서 FE 의 타입 생성기가 이 모양을 기준으로 코드를 만들어두고 있습니다.

프론트엔드 영향

  • Detail 페이지의 Decision log 섹션 페이지네이션 불가능.
  • 현재는 AgentDetail.recentDecisions 의 작은 슬라이스로 폴백해서 보여주고 "pagination coming once BE indexer exposes the full log" 라는 안내를 띄우고 있습니다. 임시로는 동작하지만 그 외 히스토리는 사용자가 볼 방법이 없습니다.

권장 수정

recentDecisions 를 채우는 데이터 소스를 그대로 페이지네이션 핸들러에 연결하면 됩니다. 필요한 쿼리 파라미터는 이미 스펙에 있습니다: limit, offset, type.

2. POST /mandate/validate 응답이 501 — schema-only stub 상태

에이전트를 새로 만드는 등록 페이지의 2단계는, LLM 이 자연어 운용 방침을 해석해서 자산 비중·락업 일수·캐리 등 숫자값을 정해주면 founder 가 그 값을 한 번 더 손볼 수 있게 해주는 자리입니다. 그런데 값을 하나라도 수정하면 백엔드가 새 값을 다시 검증하고 해시를 재계산해줘야 하는데 그 API 가 비어 있어서 매번 실패합니다. 그래서 프론트엔드는 수정을 감지하면 자동으로 원래 LLM 결과로 되돌리고 "지금은 수정 못 합니다" 안내를 띄우는 상태입니다. 결과적으로 2단계 편집 기능이 사실상 죽어 있습니다.

재현

curl -i -X POST https://web-production-acacf1.up.railway.app/mandate/validate \
  -H "Content-Type: application/json" \
  -d '{"mandate": <valid MandateSchema body>}'
HTTP/2 501
{"detail":{"error":"InternalError","message":"Not implemented yet — schema-only stub."}}

기대 동작

MandateValidateResponse 형태 — OpenAPI 가 정의한 그대로 { valid, errors, hash }. 사용자가 /mandate/parse 후 손으로 수정한 mandate 를 받아서 다시 canonical 해시 + 등록 가능한 bound body 를 돌려주는 게 목적입니다.

프론트엔드 영향

  • Launch-agent wizard (/register) Stage 2 에서 founder 가 파싱된 값을 수정할 수 있도록 만들어둔 inline 편집기 (carry / weights / lockup days 등) 가 무력화됩니다. validate 가 없으면 hash 를 다시 만들 수 없어서 on-chain 등록 시 stale hash 가 들어갑니다.
  • 지금은 FE 가 501 을 명시적으로 잡아서 원본 파싱값 + 해시로 롤백하고 모든 input 을 잠근 다음 "Manual edits paused — backend /mandate/validate isn't implemented yet" 안내를 띄웁니다. founder 는 수정하지 않은 mandate 그대로 진행하거나 Stage 1 로 돌아가 자연어를 다시 써서 재파싱해야 합니다.
  • 실질적으로 Stage 2 편집 기능이 죽은 상태이며, 미세 조정은 LLM 프롬프트 재작성이 유일한 우회 경로입니다.

권장 수정

검증 룰 자체는 이미 app/mandate/rules.py 에 있는 걸로 보입니다. 이걸 엔드포인트에 연결하고, canonical JSON 에 대해 compute_mandate_hash 를 호출하고, 필요하면 IPFS 재 pin 까지 처리하면 끝납니다.

3. 새로 등록한 에이전트의 FounderVault 가 BE 응답에 연결되지 않음

새 에이전트를 등록하면 마켓플레이스에는 약간의 인덱싱 지연 후 정상적으로 카드로 노출됩니다. 그런데 founder 본인이 자기 락업 share / 락업 만료일 / 미청구 carry 같은 정보를 보고 carry 청구 / 출금 / 강제 wind-down 액션을 눌러야 하는 두 자리 — 포트폴리오 페이지의 "Founder" 탭과 에이전트 상세 페이지의 "Structural defense" 카드 — 는 시간이 충분히 지나도 계속 비어 있습니다. 체인에는 FounderVault 가 정상적으로 만들어져 있고 디버그 API 로는 정상 조회되지만, 백엔드가 에이전트 등록 시점에 "이 에이전트의 founder vault 는 이 주소" 라는 연결 정보를 agent 데이터에 박지 않아서 일반 API 응답에서만 누락된 상태입니다. 결과적으로 founder 가 자기 자산을 어디서도 볼 수 없고 founder 전용 액션이 모두 막힙니다.

재현

  1. FE 의 /register 화면에서 founder 가 registerAgent(...) 호출.
  2. 트랜잭션 confirm. BE indexer 가 agent row 를 생성.
  3. FE 가 /agents/{id} 와 /portfolio/{address} 를 호출.

관찰된 상태 (현재 Sepolia 배포의 agent #3 기준)

출처FounderVault 데이터
GET /admin/debug/agents/3/founder-vault address 0x2a548e55… · totalSharesHeld 995e18 · lockupEndsAt 1798097437
GET /agents/3 → .founderVault null
GET /portfolio/0xfe3a… → .founderVaults [ ]

체인에는 FounderVault 가 정상적으로 존재하고 디버그 엔드포인트로는 잘 읽어옵니다. 다만 agent row 가 그 주소와 연결되어 있지 않아서 퍼블릭 응답인 detail 과 portfolio 양쪽 모두 이 정보를 누락합니다.

프론트엔드 영향

  • 직전 재배포 이후 등록한 founder 의 Portfolio "Founder" 탭이 항상 비어 있습니다. 락업된 share, 미청구 carry, 강제 wind-down 트리거 등이 전부 founder-vault 목록에 의존하기 때문에 사용 불가합니다.
  • Detail 페이지의 Structural defense 카드도 founder withdraw 진행률 / cap 진행률을 그릴 수 없습니다 (역시 data.founderVault 의존).
  • 해커톤 데모에서 founder 라이프사이클 (런칭 → carry → withdraw 등) 을 보여주려면 이 부분이 먼저 풀려야 합니다.

권장 수정

AgentRegistered 이벤트 핸들러에서 FounderVault 주소까지 함께 가져와 agent row 에 저장하면 됩니다. 이벤트 페이로드에 직접 들어있지 않다면 registry.deploymentOf(agentId).founderVault 로 한 번 더 읽어서 채워주면 충분합니다. 그 뒤로는 /agents/{id} 직렬화와 /portfolio 집계 둘 다 자동으로 정상화됩니다.

4. registry.phaseOf 와 vault.phase 가 어긋날 수 있음 (auto-advance 시점)

에이전트가 지금 어느 단계(인큐베이션 / 공개 운영 / 와인드다운 등)인지를 체인에서 두 곳의 컨트랙트가 따로 기록하는데, 이 둘이 가끔 서로 다른 답을 줍니다. 운용 vault 는 "공개 운영 중" 이라고 하는데 registry 는 여전히 "인큐베이션 중" 이라고 답하는 식입니다. 백엔드가 vault 기준으로 응답해서 사용자에게는 거의 안 보이지만, 어드민 페이지에서 "공개 운영 단계로 승급" 버튼을 눌렀을 때 한쪽은 이미 끝난 줄 알고 한쪽은 아직 안 한 줄 알아서 실패하는 경우가 생길 수 있습니다.

관찰된 상태

이전 배포의 agent #21 테스트 중, AgentVault 의 내부 phase 는 PublicLaunch 로 advance 되어 있었고 (mintsAllowed modifier 통과 + BE 의 /agents/21.phase 도 "PublicLaunch" 응답), 같은 시점 체인의 registry.phaseOf(21) 은 0 = Incubation 을 반환했습니다.

이 split-brain 은 BE 응답을 기준으로 보면 보이지 않지만 (BE 는 vault 를 미러링), 슬래시 흐름이나 Settled 전환, 그리고 registry phase 를 참고하는 외부 인덱서 입장에서 agent 가 public 인지 아닌지에 대한 해석이 갈리게 됩니다.

프론트엔드 영향

  • 낮음 — FE 는 BE 응답을 따르고 BE 는 vault 를 미러링합니다.
  • /admin/agents/{id}/qualify POST 가 vault 와 registry 의 상태 차이에 따라 AlreadyAdvanced 로 revert 될 수 있습니다.

권장 수정

vault.phase 를 advance 하는 경로 중에서 registry.advanceToPublic(agentId) 를 호출하지 않는 코드가 어디인지 확인해야 합니다. 둘이 항상 같이 갱신되도록 on-chain 단에서 lockstep 으로 묶거나, BE 가 drift 를 감지해서 advanceToPublic 을 호출해주는 reconciliation step 을 추가하면 됩니다.

5. LLM mandate 파서가 weightConstraints.asset 에 자산 심볼 대신 클래스명을 넣음

에이전트 등록 페이지에서 사용자가 "주식 60-80%, 채권 10-30%" 같은 자연어 운용 방침을 쓰면, 백엔드가 LLM 으로 그걸 해석해서 자산별 비중 한도를 정해줍니다. 그런데 이 결과가 카테고리 이름 그대로 ("주식 60-80%", "채권 10-30%") 저장되어 들어옵니다. 컨트랙트는 카테고리가 아니라 개별 자산(예: sNVDA, sMSFT) 단위로만 비중을 받기 때문에, 프론트엔드는 어쩔 수 없이 6개 자산을 1/6 씩 균등 분배(±2%)로 우회 등록합니다. 결과적으로 사용자가 원래 의도한 자산군별 비중(주식 60-80%, 채권 10-30% 등)이 등록 단계에서 사라지고, 이후 운용(rebalance)도 그 균등 비중 기준으로 돌아가게 됩니다.

관찰된 상태

일반적인 자연어 mandate ("AI mega-cap tech, equity 60-80% / treasury 10-30%, …") 를 POST /mandate/parse 에 넣으면 다음과 같은 응답이 옵니다. 

"targetUniverse": ["sAAPL","sMSFT","sNVDA","sTSLA","sSPY","USDY"],
"weightConstraints": [
  {"asset": "equity",   "minBps": 6000, "maxBps": 8000},
  {"asset": "treasury", "minBps": 1000, "maxBps": 3000},
  {"asset": "cash",     "minBps":    0, "maxBps": 3000}
]

기대 동작

weightConstraints[].asset 은 targetUniverse 에 등장하는 개별 심볼 (예: "sNVDA", "USDY") 이 들어가야 합니다. 컨트랙트의 struct WeightConstraint { address asset; uint16 minBps; uint16 maxBps; } 가 자산 단위로 받기 때문에, FE 가 심볼 → address 매핑을 하기 위해서도 이 단위가 필요합니다.

프론트엔드 영향

  • FE 는 "equity" 같은 클래스명을 SYNTHETIC_ASSETS 의 어떤 주소와도 매칭하지 못하기 때문에 6개 자산이 전부 FE 의 fallback 밴드 (10000 / N ± 200bps) 로 등록됩니다.
  • agent #3 에서 확인됨: vault.weightConstraintOf(asset) 가 sNVDA / sSPY / sAAPL / sTSLA / sMSFT / USDY 6개 자산 모두에 대해 1466 / 1866 (14.66% – 18.66%) 을 반환합니다.
  • 결과적으로 founder 가 의도한 자산 비중 (60-80% equity / 10-30% treasury) 은 등록 단계에서 조용히 사라지고, rebalance 시 계산되는 target 도 사실상 6개 균등 (~16.66%) 으로 수렴합니다.

권장 수정

LLM 프롬프트를 제약하거나 (function-call 결과를 후처리해서) weightConstraints[].asset 이 반드시 targetUniverse 에 존재하는 심볼이 되도록 강제해야 합니다. "equity 60-80%" 같은 클래스 단위 정책이 정말 필요하면 BE 가 그것을 개별 심볼 entry 로 풀어서 반환하면 됩니다. 그렇지 않으면 체인 단에서는 실제 정책이 무의미해집니다.

6. POST /admin/agents/{id}/rebalance 가 일관되게 503 으로 실패함 — 정확한 원인 미상

어드민 페이지에는 에이전트의 자산을 운용 방침대로 매수/매도하도록 트리거하는 "Trigger rebalance" 버튼이 있고, 그 위에 같은 동작을 여러 번 자동 반복해서 30일치 운영 이력을 빠르게 만드는 "Demo bootstrap" 카드가 있습니다. 그런데 이 버튼들을 누르면 매번 백엔드가 "체인에 트랜잭션을 보내려고 3번 시도했지만 실패" 라는 오류를 반환합니다. 외부에서 확인 가능한 환경 (가격 데이터, vault 잔액, 컨트랙트 비중 설정) 은 모두 정상이라서, 백엔드 내부의 트랜잭션 송신 단계에서 문제가 생기는 것으로 보이지만 정확한 사유는 백엔드 로그가 있어야 짚을 수 있습니다. 이 기능이 막혀 있어서 에이전트가 실제로 운용된 적이 없는 상태로 남고, 결과적으로 30일이 지나도 공개 운영 단계(PublicLaunch) 로 자동 승급되는 데 필요한 6개 기준 중 3개(운용 결정 횟수, 최대 손실폭, 샤프 비율)가 영원히 충족되지 못합니다.

재현

curl -i -X POST https://web-production-acacf1.up.railway.app/admin/agents/3/rebalance
HTTP/2 503
{"detail":{
  "error": "ChainUnreachable",
  "message": "rebalance failed: send_tx exceeded 3 retries"
}}

FE 가 자체적으로 확인한 사항

  • Pyth 가격 — 5종 synthetic 전부 fresh (/admin/debug/synthetic-prices 기준 sNVDA $212, sSPY $750, sAAPL $311, sTSLA $440, sMSFT $413).
  • agent #3 의 vault — 995 USDC cash 보유 중. rebalance 가 target 비중으로 매수할 자금은 충분합니다.
  • 체인 측 weightConstraintOf(asset) — 6종 자산 모두에 대해 valid band (1466 – 1866 bps) 가 등록되어 있습니다. 균등 분배 target (~1666 bps each) 이면 컨트랙트 제약을 깨지 않습니다.
  • 이슈 #5 의 클래스명 weight 문제가 executor 의 target 계산에 영향을 줄 수도 있겠지만, 체인 단의 ±200bps 폴백 형태는 정상 등록되어 있어서 단독 원인은 아닌 것으로 보입니다.

FE 가 확인 못한 부분

  • 체인 측 revert 사유 (있다면) — BE 의 503 래퍼가 ChainUnreachable 로 일괄 표현하기 때문에 send_tx 가 RPC 단에서 timeout 인지, gas estimation 단계의 revert 인지, executor wallet 의 MNT 부족인지 외부에서 구분하지 못합니다.
  • BE executor 가 weight target 을 어디에서 읽는지 — DB (클래스 단위로 저장된 mandate.weightConstraints) 인지, 아니면 체인의 address 단위 값을 다시 읽어오는지 코드 없이는 확인 불가합니다.

프론트엔드 영향

  • /admin 의 Demo bootstrap 카드가 사실상 무력화 됩니다. 시간 advance 단계는 성공하지만 rebalance 단계가 매번 실패해서, 12 cycle 을 돌려도 qualify 기준 중 #1 (continuous_days) 하나만 통과하고 #2 (decision_count ≥ 10), #4 (max_drawdown), #6 (sharpe_computable) 은 영원히 0 입니다.
  • rebalance 가 안 돌면 에이전트가 BE 의 qualification 경로로 Incubation 을 벗어날 수 없습니다. on-chain 최소조건만으로 advanceToPublic 을 호출할 수는 있지만, 그러면 performance 기록이 비어 있는 상태로 PublicLaunch 가 됩니다.

FE 가 다음으로 필요한 진단 정보
